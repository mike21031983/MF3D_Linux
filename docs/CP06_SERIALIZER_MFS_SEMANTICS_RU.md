# CP06 — 02 01 serializer lifecycle и .mfs

## Найдено в оригинальном macOS Utility (статическое дизассемблирование)

При обычном ответе `02 01` оригинальный `ConfigWidget::sysEx` проверяет флаг импорта по смещению `0xa8` (адрес `0x100104970`). Если он равен нулю, **до** пар `(tag,value)` выполняет `MidiSerializer::clear()` по `0x10010497d`.

В процедуре `ConfigWidget::importSettingsFromBlob` наоборот: по адресу `0x10010a0cf` ставится `0xa8=1`, сериализованный блок передаётся в тот же `sysEx` по `0x10010a0ea`, флаг сбрасывается по `0x10010a0ef`. Поэтому обычные ответы заменяют сериализатор, а импорт файла не очищает его.

**Следствие:** реализация CP05, объединявшая разные on-wire ответы в один «текущий профиль», могла вводить в заблуждение. CP06 исправляет это: `PassiveSerializerCapture.values` — только последний ответ; `history_values` — отдельно, только диагностика. В JSON-формате `MF3D_PASSIVE_SERIALIZER_CAPTURE_V2` статус `latest_response_only_completion_unverified` явный.

## Оригинальный .mfs

`buildMfsBlob` записывает `MidiSerializer::dump` в первый блок с длиной `u16be`. `importSettingsFromBlob` передаёт байты в тот же обработчик. При префиксе `02 01` можно **офлайн** показать пары tag/value и названия известных полей модели. После сериализатора следует набор `u16be tag/u8 version/u16be len/data`, включая RGB7 теги 1 и 2.

`mfs_container.py` теперь показывает содержимое сериализатора и длины RGB7 блоков, не меняя файл. Неизвестные значения сохраняются. **Реального экспортированного .mfs в материалах нет**, совпадение с оригинальным Utility не проверено на эталонном образце.
