# CP11 — реальные наблюдения пользователя по двум видео

Дата наблюдений: 2026-10-20. Основание: два предоставленных видео MF3D_LINUX_001.mp4 и MF3D_LINUX_002.mp4 **плюс текстовое объяснение автора**. Важнее всего именно пояснение автора: голосовые комментарии в файлах не были достоверно транскрибированы автоматически.

## Подтверждённые пользователем наблюдения (не гипотезы)

### Видео 001 — без Utility и без Ableton
- MIDI Fighter 3D просто соединён USB-кабелем с Linux.
- Без фирменной Utility устройство запускается и показывает штатную RGB-анимацию спящего режима.
- Нажатие кнопки пробуждает устройство.
- После этого заметна задержка между нажатием и срабатыванием около **0,5 секунды** (оценка пользователя; неизвестно, задерживается ли локальный LED, MIDI event, либо оба).

### Видео 002 — дополнение
- Ableton Live 12 установлен на Linux через Wine.
- В настройках Ableton MIDI Fighter 3D определяется корректно.
- В проекте Ableton MIDI Fighter 3D корректно управляет Drum Rack.
- Ранее наблюдаемая задержка исчезает.
- **После закрытия Ableton** отсутствие задержки сохраняется.
- **После перезагрузки Linux** задержка появляется снова.

## Вывод, который можно делать

USB-MIDI и базовые возможности контроллера явно работают под Linux с Ableton/Wine. Вероятно, запуск или работа Ableton изменяют временное состояние устройства либо USB/MIDI-подсистемы, и этот эффект переживает закрытие приложения, но не перезагрузку Linux. Это НЕ доказывает наличие конкретного SysEx initialization packet: Ableton мог просто открыть MIDI-port, изменить autosuspend/runtime PM или отправить MIDI-сообщения.

Отдельно: корректное имя MIDI Fighter 3D в настройках Ableton не доказывает прохождения фирменного identity SysEx 05/05 01.

## Гипотезы для проверки, не выдавать за факт

1. Ableton/Wine отправляет последовательность MIDI / SysEx, переключающую volatile режим контроллера.
2. Открытие MIDI-порта или изменение USB runtime power management отменяет suspend и задержку.
3. Спящий режим/пробуждение прошивки имеет собственный интервал, а Ableton меняет его состояние.
4. Существуют два разных вида задержки: локальная LED-реакция и доставка MIDI/звука через DAW. Нужна корректная инструментальная дифференциация.

## Приоритеты CP11

1. НЕ переходить сразу к упаковке дистрибутива: сначала локализовать причину задержки и воспроизводимый, безопасный способ инициализации.
2. Offline ревизия исходников MF3D Linux и оригинального Utility на предмет старта MIDI, handshake, sleep timer, motion animation и состояния портов; не отправлять экспериментальные write/flash.
3. Разработать пассивный захват MIDI на уровне маршрута Ableton/Wine -> USB (например, usbmon с ограничением времени), **только для одного контрольного сценария**, после подготовки инструмента. Отличать host-to-device сообщения от ответов контроллера.
4. Подготовить диагностический снимок USB runtime_pm состояния до и после открытия Ableton: power/control, runtime_status, autosuspend_delay_ms, дескрипторы USB и PID, без изменения параметров питания на первом проходе.
5. Когда есть достоверное отличие — внедрить безопасную Linux инициализацию (MIDI read-only либо подходящую настройку управления питанием) без Wine/DAW, проверить прекращение задержки и поведение после перезагрузки.
6. Сохранить уже реализованные функции CP10 (модель 0003:0001, чтение настроек, RGB, .mfs), не обещать полной 1:1 совместимости до реального теста.

## Правила

- Не требовать от пользователя серии мелких тестов; подготовить один осмысленный сценарий после статической проверки.
- GitHub Actions экономно: максимум 3 подряд при ошибках, далее расследование; на момент предыдущих этапов 0 запусков.
- Recovery ZIP каждые ~20 минут активной работы, включая код, историю, ограничения и контекст.
- Никаких EEPROM write, DFU, прошивки или factory reset до отдельной строгой верификации.
