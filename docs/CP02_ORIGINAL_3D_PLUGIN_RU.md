# CP02: результаты анализа настоящего MF3D-плагина и SysEx

Источники (приватно в recovery): пользовательский `Midi_Fighter_Utility_OSX.dmg`; извлечён `Midi Fighter Utility.app/Contents/Resources/plugins/device.mf_3d.js` размером **49885 байт**; Mach-O `Contents/MacOS/Midi Fighter Utility`. Оригинальные файлы не коммитим в публичный репозиторий.

## Что относится именно к обычному MIDI Fighter 3D

В JS: `MFR="000179"`, `FAMILY="0003"`, `model_number="0001"`, 4 банка × 16 кнопок, микроконтроллер `ATMEGA32U4`. Другие `model_number` относятся к Remix/Legacy прошивкам с другими полями и **не** должны смешиваться со стандартной моделью.

| Tag | Настройка | Диапазон / варианты | Значение по умолчанию в JS |
|---|---|---|---|
| 0 | MIDI Channel | 1–16 GUI | 3 |
| 1 | MIDI Velocity | процент / 0..127 в модельном хранении | 1.0 (100%) |
| 3 | Bank Buttons | 3 режима | 0 |
| 7 | Software Mode | Traktor / Ableton | Traktor |
| 8 | Combos | bool | true |
| 10 | Motion animation | два bitflags в битах 1 и 2 | 7 как аргумент addFlagsNonDestructive (подлежит уточнению семантики) |
| 10 | Button animation | enum в битах 3–5 | 3 (Triangle) |

## RGB-блоки оригинала

JS вызывает `CONFIG.pullBulkTransfer(1)` → inactive и `pullBulkTransfer(2)` → active, и `CONFIG.pushBulkTransfer(1,...)`, `pushBulkTransfer(2,...)` при отправке. На экспорт `CONFIG.exportData(1,1,buffer)`, `CONFIG.exportData(2,1,buffer)`. В каждом буфере 64×3=192 7-bit компонента; номера банков последовательно по 16 кнопок. Ровно `buffer[i] * 2` при загрузке (RGB7→RGB8). При записи исходный JS делит каждую RGB8-компоненту на 2; Python использует усечение до целого для неподдерживаемых дробных значений. Это гипотеза о целочисленном преобразовании в Qt, для контроля достаточно обратного преобразования при единичных тестах.

## Подтверждения по дизассемблированию Mach-O

- `ConfigWidget::sysEx` проверяет входные поля manufacturer 0,1,0x79 и распознаёт ветви payload `02 01` и `04 00`.
- `ConfigWidget::pullBulkTransfer` собирает SysEx c идентификатором `00 01 79`, началом payload `04 01` и концом F7. Подробности номера блока и синхронизации **не подтверждены**.
- `ConfigWidget::pushBulkTransfer` собирает payload с `04 00` и разбивает передачу на порции до 24 значений.
- `MidiSerializer::send` отправляет пары offset/value; точный формат, session handshake, перезапись EEPROM и отказоустойчивость ещё не установлены.
- `ConfigWidget::requestConfig` инициирует отложенную процедуру получения настроек, а не прямую запись. Таймерный callback ещё необходимо анализировать.

## Реализовано

- `device_profile.py`: независимый режим модели 0001, диапазоны и теги, 64+64 цветов RGB7, профили JSON.
- `profile_editor.py`: нативное окно Settings, Motion, подсветка по 4 банкам; выбор палитры, локальный импорт/экспорт, встроенная валидация.
- `vendor_sysex.py`: **пассивный** классификатор, в том числе для логов, без передачи SysEx.
- Локальные unit и headless Xvfb проверки; без физических тестов и без GitHub Actions.

## Осталось (по приоритету)

1. Поиск структуры формата `.mfs` в `buildMfsBlob` и `importSettingsFromBlob` для совместимости профилей Windows/Mac.
2. SysEx read-only exchange с достоверными параметрами фрейма, после полной статической верификации.
3. USB-MIDI идентификация модели/прошивки; проверка нескольких ревизий 3D.
4. Запись и проверка считыванием конфигурации — только когда риск минимален.
5. Обновление прошивки не включать до отдельной проверки безопасного пути восстановления устройства.

Ограничение: **никаких утверждений о физической работоспособности или полной совместимости 1:1 без реального теста**.
